# talkback の設計判断

talkback の設計で何を決め、なぜそうしたかの記録である。採用しなかった案も残す。設計を見直すときは、先にこの文書を読む。今の仕組みは [architecture.md](architecture.md) にある。

## 目的

- 読み上げの ON/OFF を、セッションの中から、そのセッションだけを対象に切り替えられる。
- turn の終わりを待たず、エージェントの作業中から読み上げる。
- 日本語と英語が混ざった文を、聞き取れる形で読む。
- スキルだけで配布する。hook も設定の変更も使わず、OFF の間は何も常駐させない。

## 判断の一覧

### 入力: transcript の監視

| 項目 | 内容 |
| --- | --- |
| 決定 | 両エージェントとも、セッションの transcript（JSONL）を監視プロセスで追う |
| 理由 | 両エージェントを同じ仕組みで扱え、hook も要らない。transcript にはメッセージが完結した単位で追記されるので、Markdown をまとめて解析できる |
| 採用しなかった案 | **Stop hook**: turn の終わりにしか読めない。ストリーミングで読みたいという要件に合わない<br/>**Claude Code の `MessageDisplay` hook と、Codex の transcript 監視の併用**: 行単位で早く読めるが、入力元が 2 系統になり、書きかけのブロックの扱いも要る<br/>**ACP（Agent Client Protocol）**: エディタがエージェントを起動するときのプロトコルで、普段使うデスクトップアプリや CLI のセッションには入り込めない |
| 代償 | transcript の形式は公開されていない。Claude Code のデスクトップアプリは、ツールを呼ぶ前の文を transcript に残さないことが多く、その分は読めない |

### 監視プロセス: セッションごとに起動

| 項目 | 内容 |
| --- | --- |
| 決定 | `on` でセッションごとに監視プロセスを起動し、`off` かエージェントの終了で止める |
| 理由 | OFF の間は何も常駐しない。インストールはスキルの配置だけで済む |
| 採用しなかった案 | **launchd で常駐するデーモン 1 つ**: 監視プロセスが残り続ける心配はないが、常時起動と launchd への登録が要る |
| 補足 | 終了の検知は、エージェントのプロセスの生存確認で行う。transcript が一定時間更新されなければ終了する方式は、放置しただけで読み上げが止まるので採用しなかった |

### ON/OFF の操作: モデル経由のコマンド

| 項目 | 内容 |
| --- | --- |
| 決定 | ユーザーがスキルを呼び、モデルが `talkback.ts on` / `off` を実行する |
| 理由 | スキルだけで完結し、Claude Code と Codex で操作が揃う |
| 採用しなかった案 | **UserPromptSubmit hook で `/talkback on` を横取り**: モデルを介さず即座に切り替えられるが、Claude Code だけ settings.json への登録が要る |

### 実装言語: Bun と TypeScript

| 項目 | 内容 |
| --- | --- |
| 決定 | Bun 上の TypeScript で書く。Markdown は組み込みの `Bun.markdown` で解析し、npm の依存パッケージは使わない |
| 理由 | TypeScript をそのまま実行でき、Markdown のパーサーも組み込みで手に入る |
| 採用しなかった案 | **Node.js**: 依存パッケージの同梱かインストールが要る<br/>**Python**: macOS 標準の `python3` は Xcode CLT に依存し、パッケージの導入も要る<br/>**Swift**: 読み上げを細かく制御できるが、ビルドが要り、配布物がバイナリになる |

### 読み方

| 決定 | 理由 |
| --- | --- |
| メッセージは、中間の文も最終応答も全文を読む | 当初は、ツールを呼ぶ前の文は最初の 1 文だけ読んでいた。試してみると、2 文目以降を聞き逃すのが不自然だったので変えた |
| 長い返答も打ち切らない | 打ち切る位置を決める処理が要る。止めたいときは、新しいプロンプトか `off` で止まる |
| コードブロックと表は、種類と量だけを読む | 中身を読み上げても聞き取れない。何かがあることだけは伝える |
| インラインコードは、短ければ中身を読む | 日本語の文では、インラインコードが目的語になりやすい（「`npm test` を実行します」）。消すと文が欠ける |
| パスはファイル名だけを読む | パスの前半は、聞いても役に立たない |
| 質問は、質問文だけを読み、選択肢は読まない | 選択肢まで読むと長くなる。選ぶときは画面を見る |

### 英語の読み: カタカナ化と英語の声

| 項目 | 内容 |
| --- | --- |
| 決定 | 英単語は辞書でカタカナに直し、Kyoko で読む。直せない語のまとまりと、3 語以上の英文は Samantha で読む |
| 理由 | 試聴の結果、Kyoko に英語をそのまま読ませるより、カタカナに直したほうが聞き取れた。英語の部分だけ Samantha に読ませる案も聞き比べ、辞書で直せる語はカタカナのほうが分かりやすかった |
| 採用しなかった案 | **すべて Kyoko で読む**: ファイル名やクラス名がほとんど聞き取れない<br/>**英語の部分はすべて Samantha**: 声の切り替えが多く、リズムが崩れる<br/>**識別子を「ファイル」「クラス」のような種別に置き換える**: 聞き取りやすいが、情報が減る |
| 補足 | 声を切り替えるところで間が空く問題は、区間ごとの WAV をつないで 1 回で再生する方式で解消した。試聴で違和感がないことを確認している |

### 辞書: kanalizer-dataset と上書き表

| 項目 | 内容 |
| --- | --- |
| 決定 | VOICEVOX の kanalizer-dataset（MIT、約 11.8 万語）を TSV に変換して同梱し、自前の上書き表を先に引く |
| 理由 | MIT なので、このリポジトリに同梱できる。読みは LLM で生成されていて誤り（`button` →「バトン」など）が混ざるので、上書き表で直す |
| 採用しなかった案 | **BEP 辞書**: GPL のため同梱できない。表記も「イフェクト」「パッケイジ」のように発音記号寄りである<br/>**JMdict**: CC BY-SA 4.0 の義務が生じ、英語由来の語を抜き出す変換処理も要る<br/>**推論モデル（e2k、kanalizer モデル）**: JavaScript で動く配布物がない<br/>**ユーザー辞書**: MVP の対象外にした |

### 辞書の取り込み方: 変換した TSV を同梱

| 項目 | 内容 |
| --- | --- |
| 決定 | 変換した TSV（約 3 MB）をリポジトリに同梱し、取り込んだ revision を `kanalizer.LICENSE` に記録する |
| 理由 | どのインストール方法でも、追加の手順なしで辞書が揃う |
| 採用しなかった案 | **git submodule**: 本体の JSONL が Git LFS で管理されていて git-lfs が要る。`--recurse-submodules` なしの clone や `npx skills add` では辞書が欠けるおそれがある<br/>**初回にダウンロード**: リポジトリは軽くなるが、ダウンロードと検証の処理が要り、初回にネットワークが要る |

### 割り込み

| 決定 | 理由 |
| --- | --- |
| 新しいプロンプト、スラッシュコマンド、Esc での中断で、今の発話を止めて未読分を捨てる | 読み上げ中に次の指示を出すのは、たいてい次の作業に移るときである |
| `!` で実行したシェルコマンドでは止めない | エージェントへの指示ではない。実際に `!code .` で読み上げが切れたことがあった |
| subagent やタスクの完了通知では止めない | バックグラウンドの作業が終わるたびに読み上げが切れる |
| 読み上げだけを止める `hush` を用意し、キーボードショートカットから呼べるようにする | Claude Code のデスクトップアプリでは、Esc で中断しても transcript に何も書かれないことがあり、読み上げが止まらなかった。新しいプロンプトや `off` で止めると、エージェントへの指示になってしまう |
| `hush` は、すべてのセッションの今の発話と未読分を止める | ショートカットはどのセッションから押したかを知らない。止めたいのは、今聞こえている音である |
| `hush` の合図は、シグナルではなくファイルの更新時刻で送る | 最初は `SIGUSR1` で送っていた。受け取る処理を登録していない Bun のプロセスは `SIGUSR1` で終了するので、古い監視プロセスや起動直後の監視プロセスが、読み上げごと止まってしまう |

### 複数セッション: マシン全体の再生ロック

| 項目 | 内容 |
| --- | --- |
| 決定 | マシン全体で 1 つの再生ロックを取り合い、発話を重ねない。話者が変わったら、先にプロジェクト名を読む |
| 理由 | 重なると、どちらも聞き取れない。誰の話かは、名前を聞けば分かる |
| 採用しなかった案 | **後から来た発話が割り込む**: 前の内容が途切れる<br/>**重なってもよい**: 聞き取れない<br/>**セッションごとに声の高さや速度を変える**: 日本語の声が Kyoko しかないので、区別できる幅が小さい |
| 補足 | ロックは `O_EXLOCK` で取る。当初は PID を書いたロックファイルを `O_EXCL` で作る方式だったが、PID の再利用や、古いロックの取り直しの競合に弱かった |

### Codex の sandbox: 実行ルールで sandbox の外に出す

| 項目 | 内容 |
| --- | --- |
| 決定 | talkback は sandbox の外で動かす。Codex の実行ルール（`prefix_rule`）の追加をユーザーに案内し、モデルにはルールを書き換えさせない |
| 理由 | sandbox の中では `ps` やほかのプロセスへのシグナルが拒否され、Codex の生存を確認できない |
| 採用しなかった案 | **sandbox の中で動かし、Codex だけ時間切れで終了させる**: 放置すると読み上げが止まる。Claude Code と終了の仕組みが分かれる |

### 文書の構成

| 決定 | 理由 |
| --- | --- |
| README は使う人向け、`docs/` は保守する人向けに分ける | GitHub でディレクトリを開くと最初に README が表示される |
| 文書は日本語で書く。`SKILL.md` は英語で書く | 日本語の読み上げが前提のスキルで、読み手も日本語話者である。`SKILL.md` はリポジトリの既存のスキルに揃える |
| 規則の具体的な値は、コードとテストを正とする | 文書と二重に持つと食い違う。文書には、コードから読み取りにくい理由だけを書く |

## MVP の対象外

| 項目 | 対象外とする理由 |
| --- | --- |
| カタカナの読みを登録するユーザー辞書 | 同梱の辞書と英語の声へのフォールバックで、MVP の用途は足りる |
| メッセージの生成中に行単位で読む機能（`MessageDisplay` hook） | 入力元が 2 系統になる。メッセージ単位で十分である |
| 長い返答の打ち切りや要約 | 全文を読むと決めた。止めたいときは、新しいプロンプトか `off` で止まる |
| ツールの実行許可を待っていることの通知 | 許可を求める画面は transcript に出ない。時間からの推測では、長いコマンドの実行中に誤って知らせてしまう |
| `say` 以外の音声合成エンジン | 英語をカタカナに直せば、ローカルで無料の `say` で足りる |
| Linux と Windows | `say` と `afplay` は macOS にしかない |

## 音声エンジンの差し替え

MVP は `say` だけに対応する。後から VOICEVOX などを足せるように、処理を 3 層（テキスト整形、読みの解決、合成）に分けて実装している。

`say` 以外のエンジンでは、`say` の弱点に合わせた部分がそのままでは使えない。VOICEVOX を例にすると、次のようになる。

- VOICEVOX には英語の声がない。辞書にない語を Samantha で読ませると、まったく違う声が混ざる。
- VOICEVOX のエンジンは、英単語を自動でカタカナに直す機能を持つ可能性がある（未確認）。その場合、kanalizer-dataset を引く処理は要らない。
- VOICEVOX の出力は 24 kHz で、今の 22.05 kHz とは違う。

テキスト整形と上書き表は、エンジンに関係なく使える。エンジンが英単語を自動で直す場合でも、開発用語の読みは崩れやすいと見込まれるので、上書き表は先に適用する。

そのため、今の実装は次の 3 点を守っている。

- 区間の声は、具体的な名前ではなく役割（`ja` / `en`）で持つ。役割を実際の声に割り当てるのは合成の層である。
- 区間をつなぐときの音声形式は、パイプラインの側で 1 つに決める。
- 差し替え口の細かい型は決めない。実装が `say` の 1 種類しかない段階で決めると、VOICEVOX の実際の挙動に合わず、作り直しになるおそれがあるからである。

## リスク

- **transcript の形式と、Claude Code の環境変数（`CLAUDE_CODE_SESSION_ID`、`CLAUDE_PID`）は公開仕様ではない**。どのリリースでも変わりうる。対策として、アダプタは未知の行を無視し、`doctor` で最新の行を解析できるか確かめる。
- **Claude Code のデスクトップアプリは、ツールを呼ぶ前に書いた本文を transcript に残さないことが多い**。作業中の文は一部しか読まれない。全部読むには、transcript 以外（`MessageDisplay` hook など）から本文を受け取る必要がある。
- **Codex のデスクトップアプリ**は、独自の `codex` バイナリを同梱している。切り離した監視プロセスが残るか、エージェントのプロセスをどう特定するかは確かめていない。1 つのアプリのプロセスが複数のスレッドを扱う場合、スレッドを閉じても、アプリを終了するまで監視プロセスが残る可能性がある。
- **実際の Codex セッション**では、シェルコマンドの終了時にバックグラウンドのプロセスが止められる可能性がある。モデルを使った `codex exec` はログインの期限切れで試せず、`codex sandbox` でしか確かめていない。
- **Codex のスレッドの切り替え**では、エージェントのプロセスが同じまま transcript のファイルが変わる。監視プロセスは古いファイルを追い続け、読み上げが止まる。`~/.codex/session_index.jsonl` で移り先を追える可能性があるが、確かめていない。

## 未確認の項目

次の項目は、Codex が使える別のマシンで確かめる。

1. 実際の Codex セッション（CLI とデスクトップアプリ）で、`CODEX_THREAD_ID` が rollout のスレッド ID と一致するか。
2. 実行ルールで sandbox の外から起動した監視プロセスが、シェルコマンドの終了後も残るか。
3. 祖先プロセスから `codex` のプロセスを特定できるか。デスクトップアプリでは、プロセス名が CLI と異なる可能性がある。
4. Codex の `request_user_input` を、実際のセッションで質問として読み上げられるか。
5. Claude Code の Bash の sandbox が有効なときに、sandbox の確認がどう失敗するか。

次の項目は MVP には影響しない。VOICEVOX に対応するときに確かめる。

6. VOICEVOX のエンジンが、英単語を自動でカタカナに直すか。直す場合、開発用語の読みがどの程度崩れるか。
